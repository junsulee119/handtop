# Display

External display over mini HDMI and the **Display** app (`rg35xxh-display`). Verified 2026-10-08 (hot-plug, 1080p60) and 2026-10-21 (mode list, 240 Hz).

## How it works

- Works with hot-plug: a 1080p monitor came up at 1920×1080 60 Hz, scale 1; taskbar, pointer and windows all fine. No HDMI audio device (only the analog codec appears in ALSA).
- kanshi profiles: `handheld` (DSI-1 only, runs `rg35xxh-display apply`), `docked` (HDMI-A-1 + DSI-1, runs `rg35xxh-display connected`).
- **Display app** (`rg35xxh-display`, one drawer entry "Display"; replaced the three "Display: …" entries in 2026-10). On connect it opens on the **handheld** as a layer-shell overlay; while it is open only the handheld screen is on (flag `$XDG_RUNTIME_DIR/rg35xxh-display-picker`), so the pointer cannot end up on the monitor. A 5 s countdown, restarted by any pointer movement or key, then keeps the saved layout; picking a card applies at once. Unplugging closes it. Drawn with cairo (pixel-art illustrations of each layout), follows the dark/light theme; `--preview FILE` renders it to a PNG.
- Layouts (`~/.config/rg35xxh/display-mode`, also `rg35xxh-display set monitor|extend|mirror`):
  - **monitor** (default): handheld screen off (backlight off too). Pressing X turns it on as a full-screen keyboard panel — see [the on-screen keyboard](../services/on-screen-keyboard.md).
  - **extend**: handheld screen **below** the monitor, centred (x = (monitor width − 640) / 2, y = monitor height): the pointer crosses off the monitor's bottom edge in its middle third. Width and height are the monitor's size in layout coordinates: its mode divided by its scale, swapped when it is turned 90°/270° (a 4K monitor at scale 2 counts as 1920×1080). Handtop's kanshi profile always sets scale 1, so this matters only when a user changes the scale or rotation themselves (codebase audit 2026-10-30, M09; before, the physical size was used, which left a gap between the screens). The pointer-speed layout below uses the same size. Tested on the device (2026-11-02, Hansung 1080p at `--scale 2`): handheld at 160,540, pointer layout 960×540, the pointer crosses the bottom edge onto the handheld.
  - **mirror**: the monitor switches to 640×480 at the same position as the handheld, so both show the same picture (the monitor scales it up).
- **Resolution / refresh rate**: lists of the monitor's modes (largest first, refresh rates per resolution; the preferred mode marked) with scroll bars. **Test** turns the monitor on in that mode, apart from the handheld (x = 4000, no shared edge), and asks "Keep this mode?" for 15 s; otherwise it switches back. The 15 s are real time (`time.monotonic()`), not counted UI ticks, and every `wlr-randr` / `notify-send` call has a time limit (5 s / 3 s), so a slow or stuck call can delay the switch-back by at most that long instead of holding it up for good (codebase audit 2026-10-30, M10). Tested on the device (2026-11-02): a Test not kept switched back after 15 s. As before, the monitor then stays off while the picker is open (handheld only, see above) and comes on in the kept or preferred mode when a layout is picked or the picker closes. A separate watcher process was considered and rejected: what it would guard against is the compositor hanging, and then its own `wlr-randr` call could not switch back either. Kept modes are stored per monitor (make + model + serial) in `~/.config/rg35xxh/display-modes.json`; otherwise the default mode (below). Refresh rates are passed exactly as listed (`1920x1080@239.998Hz`): wlr-randr calls a rounded value an "unknown mode". Verified 2026-10-21: 1080p 240 Hz on a Hansung TFG24F24P runs a real 570 MHz TMDS / TCON clock (60 Hz: 148.5 MHz).
- **Pointer speed per screen**: after each layout change the tool writes the enabled outputs and a speed factor (diagonal ÷ 800, the handheld's; 1080p ≈ 2.75) to `$XDG_RUNTIME_DIR/rg35xxh-pointer-layout`. The input daemon follows the pointer over that layout (its own relative motion, clamped like wlroots) and scales the stick / D-pad speed by the factor of the screen it is on (`display_speed_scale` in `input.conf`, 0 = off). It moves the pointer to the layout's top-left corner when a two-screen layout starts, so the estimate starts exact; its virtual mouse has no libinput acceleration (labwc `rc.xml`), so the estimate stays exact. Motion from other mice is not seen.

## Default mode, the layout check, notifications (v0.3.9)

Found 2026-11-06 on a 1920×1200 monitor: the Display app listed nothing above about 1600 wide, Monitor only left the monitor at 1920×1200 with **no taskbar and a slow pointer**, and the input daemon's log showed an empty pointer layout (`[] -> x1.00`). The monitor's preferred mode was most likely beyond what the H700's HDMI accepts (1920×1200 at 60 Hz needs a slightly higher pixel clock than 1080p), so it was missing from the mode list; v0.3.8 still asked for it with `wlr-randr --preferred`, and the monitor ended up in a mode outside the list, which none of the code that reads the list could handle. Not reproduced on that monitor yet; the fixes below are made to hold whatever the exact cause.

- **Default mode**: the monitor's preferred mode if it is listed; otherwise the largest listed mode, at the refresh rate closest to 60 Hz, among the modes with the screen's own shape (from its physical size in the EDID; a 16:10 screen gets 1680×1050, not a stretched 1600×1200). Every mode is set explicitly from the list (`--mode WxH@RHz`), never with `--preferred`.
- **Check after every layout change** (`check()`): the monitor, when it should be on, must be on in a listed mode. If not, the default mode is tried once; if that fails too, the handheld screen is turned on so there is always a usable screen, and a notification says to pick another resolution. With no monitor, the handheld screen is turned on if it is off.
- **Pointer layout**: retried for up to 3 s when no output is on with a known mode, and never written empty; the input daemon also ignores an empty layout and keeps its speed (`daemon.py`, tests in `test_daemon.py`).
- **Notifications** (`makoctl reload` after each layout change): mako 1.10 keeps a toast on the screen it opened on. When that screen went away (the resolution "Keep" toast opens while only the handheld is on, then the picker closes and the handheld goes off), the toast stayed frozen on the monitor at the handheld's top-right corner (x = 632, so it looked like the left side), long after it expired, and new notifications never showed. Reproduced 2026-11-06 on the Hansung; `makoctl reload` cleared it and new toasts showed top-right on the monitor.
- **One toast, after the picker closes**: "Monitor only · 1920x1080 @ 60 Hz" (the layout and the monitor's mode), only when a layout was picked or a resolution kept. It is sent 2.5 s after the switch and stays 5 s: a monitor just switched on or to a new mode is black for 1–2 s while it syncs, and a toast sent at once (shown fine in a screenshot, which the compositor takes) was over before the monitor showed a picture. Before, Keep showed "Resolution: …" at once, while only the handheld was on: it was gone after 2.5 s, before anyone looked back at the handheld, and it was the toast that froze (above).
- **Log**: `~/.local/state/session/display.log`, appended across sessions (trimmed to its newer half past 256 KB): each layout change with the mode, whether the picker is open, and every output's state, current mode, number of modes and preferred mode, plus what the check did.
- **Monitor unplugged**: a toast says the picture is back on the handheld screen ([../services/device-notify.md](../services/device-notify.md#monitor-unplugged)).
- **Taskbar**: Waybar runs under `rg35xxh-waybar`, which restarts it if it exits ([desktop.md](../desktop.md#shell-components-waybar--nwg-drawer--wlogout)).
